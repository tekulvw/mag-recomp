# Profile and tool contract (schema version 1)

Profiles are maintainer-owned files shipped alongside this tooling. The release CLI accepts known bundled IDs only. Game directories never provide commands/profiles. Editing a profile or application source is a trusted development operation; JSON hashes establish identity, not an independent signature/trust chain. Production profile signing/update trust is a release integration gap.

The loader rejects unknown fields, unknown schema versions, nonportable relative paths, duplicate input paths, unreviewed ready recipes and unknown platform/architecture keys. A production ready adapter requires reviewed input identities, nonempty generate/build/package stages and a package file allowlist. The shipped MAG profile is deliberately unconfigured and blocked on every host.

Top level: `schema_version` = 1; lowercase portable `id`; positive integer `revision`; `kind` = production or synthetic; `approval` = reviewed or unconfigured; `identity`; and `platforms`.

`identity` has human-readable `label` and `provenance` plus `inputs`: exact ordinary relative file paths with byte `size` and lowercase `sha256`. All required real inputs must eventually be represented by a reviewed manifest/materialization graph. Symlinks are unsupported. Original inputs are hashed and copied into an installation-private read-only snapshot; commands receive that snapshot path rather than the original source path.

`platforms` maps exact windows/linux/macos + x86_64/arm64 keys to `status`, `reason`, `tools`, `stages` and `package`. Unknown/foreign hosts never fall back to another architecture.

Each tool record requires `id`, exact `version`, HTTPS `url`, archive `sha256` and `size`, `format` (zip or tar.gz), `max_expanded_size`, `max_entries`, relative `executable` and `license` metadata. Tool IDs are unique per adapter. These fields do not substitute for a publisher/license review. Archives cannot contain links, devices, sparse files, encrypted entries, duplicate/case/Unicode-colliding file paths or paths that escape the extraction root. TAR decompression includes a bounded metadata/padding allowance of 4096 bytes per entry plus 10240 bytes before parsing. Archives and cached blobs are rehashed before use. Cancellation/error removes partial downloads; retries restart from zero. No real tools are pinned in the initial profile.

Each stage has `name` (generate, build, package in order), `tool` (a pinned tool ID), `argv` (string array) and `outputs` (required ordinary files relative to the work directory). Arguments may expand `{input}`, `{work}`, `{tools}` and `{package}` through Python format syntax; `{package}` is a recipe work subdirectory, never the final publication tree; literal braces require escaping. The executable always comes from the verified tool root. No shell or user-input-directory executable search occurs. The child environment excludes inherited credentials, compiler flags, Python paths and unpinned PATH entries. No subprocess is an OS sandbox: recipes/tools must be trusted.

`package` is an exact list of ordinary files relative to work that enter the local application result. Installer SOURCE distribution uses a separate fixed registry and never scans source assets, generated code, local apps, staging, tool caches or account directories. The `bundle` command is source tooling only, with `release_ready=false`.

A sibling `.DEST.mag-staging` directory contains the local journal, private inputs, tool extraction, work and logs. Output must not exist. A sibling lock file coordinates one job per destination. Only a successful atomic `O_CREAT|O_EXCL` open establishes that this installer created a fresh lock and may initialize it. On `EEXIST`, Windows or a call without explicit resume refuses immediately; explicit POSIX resume opens without `O_CREAT` and requires existing valid metadata. If that existing file disappears before opening, the operation fails rather than recreating it. On POSIX the lock intentionally persists: an open descriptor owns a nonblocking exclusive kernel `flock` for the whole transaction, and the installer never unlinks/recreates that inode based on PID metadata. Recorded PIDs are informational only. `--resume` requires unchanged profile digest, host, source/destination and input identity, then replays work into fresh owned staging subdirectories. It never trusts a half-finished build. Explicit POSIX resume must acquire the same kernel lock; an active holder is refused. Every preexisting POSIX lock requires nonempty valid `posix-flock` metadata before any rewrite or staging access. Existing empty, legacy PID-only or malformed lock metadata remains fail-closed for manual inspection, rather than being migrated while an older installer could still be active. Windows stale-lock recovery is not certified and retains existing locks without any signal probe. Lock release/close errors and failures while reporting them are best-effort local cleanup notices: committed success still returns success, and a precommit failure remains the original exception. A failed failure-journal write is secondary too. Atomic publication refuses existing destinations through the host adapter.
