# Controls settings integration

The existing macOS MAG Settings window offers General and Controls pages when an input integration registers its supported action catalog. Controls has separate Keyboard & Mouse and Controller pages, two binding slots per action, explicit conflict replacement, clear and per-device reset. Mouse sensitivity and vertical inversion affect the existing relative mouse aim path. Aim assist cannot be enabled for KBM.

Bindings are physical USB HID key positions, zero-based mouse buttons, or normalized controller button codes. Controller codes0–31 use SDL's button numbering;32 and33 are left and right triggers. A runtime must reject unsupported physical controls before saving, rather than accept a binding it cannot implement. Game-specific action identifiers and native routing remain outside this repository.

`player_controls_settings.h` is the portable frontend contract. Register defaults, descriptors, a preferences path, pure capability validation and a queue-only apply callback. Descriptors remain complete when a user unbinds an action. Sources is a bit mask (keyboard1, mouse2, controller4). The panel supports OnFoot context1 and Menu context16. The binding-scope selector edits one context at a time, preserving bindings in the other context. Optional descriptor groups separate native menu/command buttons from ordinary gameplay actions. Other frontends can reuse the service and Rust `mag_input_edit_binding` boundary without AppKit. The Windows host capture adapter and native settings frontend still require implementation and runtime verification.

An optional extension `prepare(elf)` runs before settings and guest allocation, permitting a catalog to be registered for first-run setup without constructing native input state. Existing extension `start` timing is unchanged. With no integration registered, behavior stays unchanged.

Schema2 added `controller_remap`. False keeps digital controller input on the native path and displays the runtime's default controller map. Editing or clearing a controller binding sets it true; the integration then replaces the complete supported digital action set, including explicitly unbound actions. Reset Controller restores defaults and native digital routing. Schema1 files load with controller_remap false. Schema3 adds an integration-defined `catalog_revision`; schema1/2 load with revision0. A pure registration upgrade callback can add new action defaults to a copied profile once, avoiding conflicts with existing custom bindings. Saving records the revision so explicitly unbound new actions stay unbound. Loading never rewrites the file. Unknown schemas and damaged files remain untouched and visible as errors.

The service validates a copied draft, saves atomically, then queues it for the runtime. It never configures the input engine from the UI thread. Bindings affect on-foot gameplay and its supported HUD actions. Frontend controls without an owned gameplay actor and positively paused contexts remain native; generic fullscreen UI resources are not independently classified. The native adapter installs a validated revision at its input boundary, cancels pending old input and preserves process-wide KBM provenance. A startup input-mode environment override is identified in the panel; Apply uses the selected saved mode. Controller analog movement and look retain the native response.

While settings are open, gameplay input is blocked. Binding capture temporarily chains the existing keyboard/mouse callbacks, filters held controls, consumes local AppKit input, cancels on focus loss, device-page changes, Escape or a15-second timeout, and restores callbacks conditionally. Controller capture uses fresh button edges and trigger hysteresis (press≥0.55, release≤0.45). Closing settings requires fresh gameplay activation; captured presses must not become gameplay actions.

Apply controls saves only the Controls page. General retains its existing Apply, display confirmation and rollback behavior. Cancel discards drafts on both pages. In startup setup, Play saves both pages before launch. Controls profile errors do not replace the file automatically.


Native shared buttons can span OnFoot and Menu. The portable engine retains only physical contributors whose action and behavior are mapped in both contexts for the same owner. Nonshared gameplay input and mouse motion cancel; owner/focus/profile/device resets still revoke the affected input. Recognizers retain the exact surviving pulse, avoiding another Down when Start opens a menu. An explicit shared-native-action list separately permits native-controller recognizers to cross the same-owner transition without a host offer. This does not preserve canceled host pulses.

In Menu, releasing relative mouse capture clears motion while keeping valid mouse-button input. Focus/device loss still cancels it. The desktop mouse-enabled gate releases/reacquires relative mode without uninstalling the keyboard collector. Menu frames never export mouse aim or controller look output and must not be accepted as gameplay provenance.

Controller capture includes Select/Back, Start/Menu and all four D-pad directions. Guide remains reserved. The runtime still supplies capability validation; support for a physical input alone does not prove every native action/context is implemented. Native-button routing must preserve the original callbacks, traversal and channel-consumption behavior, including button release for HUD interactions.

A native adapter adopting an already recognized controller hold can seed the portable recognizer with its semantic phase, normalized value and age. The seed emits no event and ignores prior event bits. Its original hold clock continues when a new host source joins; completed fresh host clicks keep their existing physical-duration timing. Adapters can also supply native-channel contribution explicitly, so remapped Controller offers and an actual native controller hold are not conflated during context changes. Configure cancels old recognition state.
